# SC01 – Intelligent Campus Climate and Energy Controller

## 1. Project Overview

SC01 is an Intelligent Campus Climate and Energy Controller that recommends room cooling, fan operation, and energy-management actions based on environmental conditions, occupancy, and electricity tariff levels.

The project compares two approaches:

- **Rule-Based Baseline Controller:** Uses predefined temperature, humidity, occupancy, and tariff rules.
- **Soft Computing Fuzzy Controller:** Uses fuzzy logic to generate cooling recommendations and applies project rules to determine fan levels and energy actions.

The project also includes controller comparison results, visualization charts, and an interactive Streamlit dashboard.

**Intended user:** A campus facility manager who needs understandable room-climate recommendations while considering energy usage.

**Important limitation:** The project uses synthetic scenarios for software development and testing. The generated data does not represent actual campus measurements or a certified building-control system.

## 2. Problem Statement

Given a room's temperature, relative humidity, occupancy count, and electricity tariff category, the system recommends:

- Cooling percentage
- Fan operating level
- Energy-management action

The project evaluates how a deterministic rule-based controller and a fuzzy logic controller respond to the same input conditions.

## 3. Input Variables

| Input | Description | Unit or allowed values |
|---|---|---|
| `scenario_id` | Unique identifier for a scenario | Text |
| `temperature_c` | Room temperature | °C; configured range 18–45 |
| `humidity_pct` | Relative humidity | %; configured range 20–100 |
| `occupancy_count` | Number of people in the room | Integer, 0–100 |
| `tariff_level` | Electricity tariff category | `low`, `medium`, `high` |

The generator produces 10,000 synthetic scenarios using a fixed random seed of `42`.

The configured target probabilities for tariff levels are:

- Low: 35%
- Medium: 35%
- High: 30%

Actual counts may differ from the target proportions because the values are randomly generated.

## 4. Output Variables

| Output | Description | Allowed values |
|---|---|---|
| `cooling_pct` | Recommended cooling level | 0–100% |
| `fan_level` | Recommended fan operating level | `off`, `low`, `medium`, `high` |
| `energy_action` | Energy-management recommendation | `normal`, `save`, `avoid_peak` |

These outputs are generated by the controllers. They are not columns in the original five-column input dataset.

### Step 3 — Baseline Controller

Implementation: `src/baseline_controller.py`

The baseline controller applies the following rules:

1. If occupancy is zero, cooling is set to 0% and the fan is turned off.
2. If occupancy is nonzero and temperature is below 24°C, cooling is set to 10%.
3. If temperature is between 24°C and 30°C inclusive, cooling is set to 50%.
4. If temperature is above 30°C, cooling is set to 90%.
5. If humidity is above 75%, the fan level is increased by one level when possible.
6. If the tariff is high, the energy action is `avoid_peak`; otherwise, the baseline action is `normal`.

The zero-occupancy rule takes priority over the other cooling and fan rules.

### Step 4 — Fuzzy Controller

Implementation: `src/fuzzy_controller.py`

The fuzzy controller uses fuzzy membership functions and inference to calculate a cooling recommendation. The controller considers temperature, humidity, and occupancy for cooling inference, then derives fan and energy actions according to the project's implementation rules.

Further design details are documented in `docs/STEP-4.md`.

The fuzzy controller is compared with the baseline using the same scenarios so that differences in recommendations can be examined.

## 8. Scenario Coverage and Testing

Testing should distinguish between the following scenario categories:

- **Normal scenarios:** Typical combinations of temperature, humidity, occupancy, and tariff.
- **Boundary scenarios:** Inputs at or near configured limits, such as 18°C, 45°C, 0% or 100% humidity, and occupancy values of 0 or 100.
- **Stress scenarios:** Difficult combinations, such as high temperature, high humidity, high occupancy, and high tariff.
- **Invalid scenarios:** Inputs that violate the data contract, such as nonnumeric temperature values or unsupported tariff categories.

An invalid test fixture is maintained at:

`data/test/invalid_input.csv`

It includes an invalid temperature value (`abc`) for validation testing.

The generated dataset's documented range variation and the invalid fixture provide part of the testing evidence. Explicitly labelled normal, boundary, stress, and invalid cases should be maintained and verified against the controller and validation requirements before claiming complete scenario coverage.

## 9. Assumptions and Limitations

- The generated scenarios are synthetic and are intended for software testing and controller evaluation.
- Temperature and humidity ranges are project configuration assumptions, not proof of compliance with an indoor-comfort standard.
- Occupancy is represented as a count from 0 to 100.
- Tariff values are categorical and do not represent actual electricity prices.
- The project does not model every real-world building, HVAC system, weather condition, or occupant preference.
- Background resources such as ASHRAE Standard 55, EPA indoor-air-quality resources, and Bureau of Energy Efficiency resources provide context; they are not the source of the generated records.
- No third-party dataset is used for the generated scenarios, and no separate dataset licence has been assigned to them.
- The controller outputs are educational decision-support recommendations, not certified operational instructions.

```bash
git diff --cached --check
```

Commit the changes with a descriptive message:

```bash
git commit -m "Document project and add interactive dashboard visualizations"
```

Push to the intended remote branch only after confirming the current branch:

```bash
git push origin step-4-fuzzy-controller
```

Finally, verify the repository state:

```bash
git status --short
git log -1 --oneline
```

A successful commit saves the changes locally; a successful push publishes them to the remote branch. Do not claim the work is synced until the push has completed successfully.
